## 设计时基线与证据

- `src/rayon_executor_service_state.rs` 在同一 mutex 下管理接纳、队列、运行和取消计数；取消清理在锁外完成，期间仍占容量。
- `src/rayon_executor_service.rs::run_one` 在 `job.run()` 外层使用 `let _ = catch_unwind(...)`，然后调用 `finish_running()` 并按需派发后继任务。
- `src/rayon_task_handle.rs` 的取消路径及服务的 `stop` 路径显式使用 `internal::discard_panic_payload`；该 helper 会隔离 payload 析构再次 panic，并有意遗忘次级 payload。
- `tests/panic_payload_cleanup_tests.rs` 覆盖取消和 stop 的 payload 清理；`tests/rayon_task_handle_tests.rs::test_rayon_task_handle_reports_panicked_task` 覆盖普通运行 panic 的结果。
- 本地 `rs-executor/src/task/task_runner.rs` 和 `task_state.rs` 已对任务调用、detached 结果丢弃及结果发布作异常隔离。实施时需检查 Cargo 实际解析的依赖版本与源码，不能将相邻 checkout 等同于构建所用依赖。
- `rs-execution-services/src/execution_services/waiting_submission.rs::submit_cpu_callable_wait` 通过 `capacity_changes()` 重试 CPU 提交；故运行计数不归还会影响下游背压与关闭，但本轮尚未证实存在这样的可达故障。
- `doc/user_guide.md` 的 Errors and Diagnostics、`doc/user_guide.zh_CN.md` 的“错误与诊断”未限定 get/await 错误传播说法的适用提交类型。

上述为静态评审证据，尚未进行动态复现或实施验收。

## 方案选择

采用“服务级回归测试 + 双语说明 + 证据驱动的局部修复”。保留现有有界队列、调度预约、生命周期、通知类型和公共 API。

不选择全面重写 panic/调度框架：目前没有收益证据，且会引入新的并发风险。不选择无条件修改 RE-003：当前底层已包含多层隔离，必须先证明可达性或明确防御性收益。无需破坏兼容性、升级依赖或要求下游迁移。

## RE-001：运行阶段回归矩阵

新建 `tests/running_resource_tests.rs`，通过公开提交 API 建立单 worker 服务，容量设为 1 或 2。使用 channel 控制执行顺序，并使用原子计数观察执行和析构次数。每个测试都设置 10 秒整体等待上限；先确认运行，再放行异常路径，避免依赖 sleep 或调度速度。

至少覆盖以下情况：

| 场景 | 观察点 |
| --- | --- |
| callable 运行时抛出析构会再次 panic 的 payload | handle 返回 Panicked；正常后继任务执行一次；容量恢复；关闭完成 |
| detached runnable 返回析构会 panic 的错误值 | 提交成功；错误析构被隔离；后续工作及终止正常 |
| 在任务返回前丢弃结果句柄，成功结果析构 panic | 无接收者的结果清理不破坏 worker 调度与计数 |
| 在任务返回前丢弃结果句柄，错误结果析构 panic | 与成功结果同等验证，避免只覆盖 Ok 分支 |

结果句柄存在时先用 `try_get` 或受超时约束的 async 等待取得结果，避免无限阻塞。观察结果可用不等于容量已经释放；用有截止时间的重试提交后继任务判断容量恢复，而非立即断言提交一定成功。最终 shutdown 后 `wait_termination_timeout` 必须返回 true，stats 的 queued/running/cancelling 均为零。

次级 payload 的析构计数应为零，原始 payload 或结果的应执行析构计数应为一次。用子进程隔离可能触发 Rayon 默认 abort 的案例，父进程设置超时并检查退出状态；不能让单个异常案例直接终止整个测试套件。不得为测试生产私有 helper 添加公开 API。

## RE-002：双语错误观察边界

仅修改两份用户指南中对应段落，并在 detached 概念说明处加简短交叉提示。英文核心文案：

> For submissions that return a result handle, task failures and panics are observed through `get` or `.await`. Detached `submit` returns only admission status and discards the final task result. Use a callable submission when the caller needs to observe failure, or report failures from the detached task itself.

中文对应文案：

> 对于返回结果句柄的提交，任务失败或 panic 通过 `get` 或 `.await` 观察。detached `submit` 只返回接纳状态，并丢弃任务最终结果。调用方需要观察失败时，请改用 callable 提交，或由 detached 任务自行报告错误。

不承诺自动日志、全局错误回调或 detached 结果恢复。不为此扩展 API。README 当前已有 detached/结果句柄区分，无需重复改写；rustdoc 若实施核查发现相同歧义，仅作相同边界的最小补充。

## RE-003：核查与条件修复

1. 记录 Cargo 解析出的 `qubit-executor` 版本及源码位置；阅读 `TaskRunner`、slot 完成、结果丢弃和 hook 通知路径，确认哪些异常可越过 `job.run()`。
2. 以公共提交 API 尝试复现；优先复用 RE-001 案例，不使用替换私有 QueuedJob 的注入来声称公共路径可达。涉及 abort 的复现必须在有超时的子进程中进行。
3. 如证实逃逸 payload 析构可在 `finish_running` 前再次 unwind，记录失败测试，最小修改为以下替换，沿用现有 helper：

```rust
if let Err(payload) = catch_unwind(AssertUnwindSafe(|| job.run())) {
    crate::internal::discard_panic_payload(payload);
}
```

随后保留原有 `finish_running` 和后继派发流程。验证修复前失败、修复后通过。
4. 如果没有找到当前公共 API 可达路径，记录“未复现/静态路径已隔离”，不得将其标为已确认缺陷或已修复。默认保留源码；若决定采用同一替换作为防御性一致性调整，必须先记录当前隔离边界之外的具体收益和 helper 级测试证据，并明确这不证明用户路径存在故障。不得借机引入新 guard 框架或修改其他仓库。

本方案优先选择未复现时不修改生产代码，避免仅为猜测增加变更。未来依赖差异或新证据可改变分支选择，但须同步更新核查记录。

## 验收与风险

验收包括新增矩阵测试、现有取消/并发/容量等待测试，默认与 all-features 测试、rustdoc 检查、项目 CI 和既有 coverage 门槛。完整命令由实施计划列出，不能以“本阶段仅编写文档”为理由跳过未来验证。

不降低 coverage 阈值，不用忽略测试、生产 coverage cfg、删除断言或吞掉测试失败取得通过。若基线失败，允许必要的源码与测试修复，记录原因、改动及重跑结果；实际涉及新 API 或跨仓依赖变更时先重新评估范围，不直接扩张。

风险主要是异常案例触发进程 abort、同步测试卡住，以及结果可见与容量回收的短暂时差。通过子进程隔离、截止时间和 channel 顺序控制解决。双语文案须语义一致。现有架构与 API 保持兼容，`rs-execution-services` 不需要迁移；其 CPU 等待与关闭测试可作为针对性下游验证。
